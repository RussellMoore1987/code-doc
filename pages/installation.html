Installation

This guide walks you through getting DevDocs running locally on your machine. There is no build step, no package manager, and no framework - just a few files and a local HTTP server.

Prerequisites

Before you begin, make sure you have one of the following available:

  • VS Code with the Live Server extension installed, or
  • Python 3.x - ships with a built-in HTTP server, or
  • Node.js - use the npx serve package if preferred.
ℹ Tip

Any HTTP server will do. The only real requirement is that files are served over http:// or https:// so the Fetch API works correctly. A file:// origin will fail with CORS errors.

Download the Project

Clone this repository or download the ZIP and extract it to a local folder:

# Using git
git clone https://github.com/RussellMoore1987/code-doc
cd code-doc

# Or download the ZIP and extract:
unzip code-doc.zip
cd code-doc

The project directory should look something like this after extraction:

code-doc/
├── index.html
├── styles.css
├── app.js
└── pages/
    ├── image-galleries.html
    ├── installation.html
    ├── intro.html
    ├── tools.html
    ├── videos.html
    └── ...

Starting a Local Server

Option A - VS Code Live Server

  1. Open the code-doc folder in VS Code.
  2. Install the Live Server extension (Ritwick Dey) if you haven't already.
  3. Right-click index.html in the Explorer panel and choose Open with Live Server.
  4. Your browser will open automatically at http://127.0.0.1:5500.

Option B - Python HTTP Server

From inside the project folder, run:

# Python 3
python -m http.server 8080

# Then open in your browser:
# http://localhost:8080

Option C - Node.js serve

npx serve .
# Opens at http://localhost:3000 (or the next available port)

<title>My Project Docs</title>
...
<span class="brand-title">My Project</span>

Navigation Structure

Open app.js and edit the NAV_DATA array near the top of the file. Each section group has a label and a children array. Each leaf item needs an id, a label, and a page path.

ℹ Tip

When you're finished editing the navigation structure, comment out the DevDocs-specific navigation entries instead of deleting them. This keeps them available for future reference while ensuring they don't interfere with your custom navigation structure. 

const NAV_DATA = [
  {
    id: 'my-section',
    label: 'My Section',
    children: [
      { id: 'page-one', label: 'Page One', page: 'pages/page-one.html' },
      { id: 'page-two', label: 'Page Two', page: 'pages/page-two.html' },
    ]
  }
];

NAV_DATA Property Reference

Property Required Description
id Yes A unique string identifier for the item. Used in the URL hash (e.g. #my-section), deep-linking, scroll-spy, and programmatic navigation. Must be unique across the entire NAV_DATA tree — duplicates will cause routing conflicts.
label Yes The human-readable text displayed in the left sidebar navigation tree. Can include spaces and mixed case.
page Leaf items only Relative path to the HTML fragment file that gets loaded into the content area when this item is clicked (e.g. 'pages/my-page.html'). Omit this on group items that only serve as collapsible containers.
children Groups only An array of nested nav items. Items with children render as collapsible groups in the sidebar. A single item cannot have both page and children — use one or the other.

Note on nesting depth

The tree renderer supports up to four levels of nesting. Beyond that, indentation will continue to work but may become visually tight at narrower sidebar widths. Three levels is recommended for most projects.

Adding Pages

Each documentation page is a plain HTML file inside the pages/ directory. Pages must:

  1. Be wrapped in a single <div> element. (does not have to be wrapped in <div>, just preferred)
  2. Use heading tags (h1-h4) with unique id attributes (or let app.js auto-generate them from the heading text).
  3. Contain only the page body - no <html>, <head>, or <body> tags.
ℹ Note/Tip

You may need to add a bare </body> tag at the very end of your HTML fragment when all three of the following are true:

  • You are serving the project with VS Code Live Server.
  • Your fragment ends with a complex, multi-line element - such as a slider, a deeply nested component, or a large table.
  • The fragment contains no </body> tag.

VS Code Live Server injects its live-reload <script> by searching each served file for </body> and inserting just before it. When that tag is absent, Live Server falls back to appending its script inside the last open element, which truncates the rendered content. Adding a lone </body> at the end of the fragment gives Live Server a safe injection point without affecting how app.js fetches and renders the page. See sliders.html for a working example. 

<!-- pages/my-page.html -->
<div>
  <h1>My Page Title</h1>
  <p>Your content here.</p>
  <h2 id="section-one">Section One</h2>
  <p>More content.</p>
</div>
⚠ Heads up

If you omit id attributes from headings, app.js will auto-generate them from the heading text using a slug algorithm. This is convenient but means IDs can change if you rename headings. Use explicit IDs for any anchor links you share with others.
